# Ясный шаг — техническое описание и API

Версия 1.0, 15.11.2026. Нормативный объём первой поставки определён в [requirements.md](requirements.md). Здесь зафиксировано предлагаемое техническое решение для реализации этого объёма. Конкретный стек не был выбран пользователем; менять его можно через короткий ADR при сохранении требований и API.

## 1. Компоненты и развёртывание

Рекомендуемый исходный вариант: TypeScript, React для веб/PWA, IndexedDB для локальных данных, Node.js HTTP API, PostgreSQL для сервера. Версии и конкретные библиотеки выбрать по официальной документации в начале реализации, закрепить lock-файлом; номер версии в этом документе не задаётся.

```text
Веб / PWA
  UI → доменные команды → IndexedDB + локальная очередь операций
                                ↕ HTTPS /api/v1
Внешний инструмент → API → авторизация → обработчики команд → PostgreSQL
                                                     ↘ журнал изменений
Будущие Android/iOS → тот же API и тот же протокол синхронизации
```

Клиентский UI читает локальную БД, а не ждёт GET после каждого действия. Репозитории данных отделены от компонентов. Сервер повторяет обязательную валидацию и проверку прав, не доверяет клиентской проверке. Формат команд не зависит от браузера. Web-специфические service worker, IndexedDB и cookie-сессия находятся в адаптерах клиента.

На сервере пользователя: Nginx завершает TLS, отдаёт статическую оболочку и проксирует `/api/v1` на приложение. API и БД слушают внутренние интерфейсы; база не публикуется в интернет. Клиент и API одного origin. Предлагаемый способ поставки — контейнеры приложения/БД либо эквивалентная документированная установка; Nginx можно использовать существующий. Производственное развёртывание выполняется только после выбора домена/хоста и отдельного поручения, подготовка инструкции входит в R1.

## 2. Модель данных

Общее для пользовательских сущностей: `id: UUID`, `ownerId`, `revision: integer`, `createdAt`, `updatedAt`, `deletedAt?`. Времена событий — UTC от сервера, локальное время создания можно сохранить отдельно как метаданные. Клиент генерирует UUID до отправки; время устройства не определяет победителя конфликта. Серверные revision монотонно возрастают для объекта. `ownerId` определяется аутентификацией, не принимается из пользовательского payload.

| Объект | Поля и правила |
|---|---|
| User | login, passwordHash, timeZone (IANA), credentialsVersion. Публичной регистрации нет. |
| Project | title, visionMarkdown, targetMarkdown, planMarkdown, status: active/paused/completed/cancelled. Пустые vision/target разрешены; UI показывает необходимость уточнить. |
| Task | projectId?, title, notesMarkdown, status: open/done/cancelled, inActions, planPosition, dueDate?, completedAt?, completedFromActions. |
| ActionQueue | Один объект на владельца: orderedTaskIds[], revision. Порядок общий; план проекта имеет собственный порядок. |
| InboxItem | bodyMarkdown, status: unprocessed/processed, processedAt?, sourceLabel?. |
| ProcessingDraft | inboxId, outputs[] с заранее созданными UUID и ссылками, revision. Пользовательский черновик разбора синхронизируется. |
| OriginLink | sourceType/id, targetType/id, relation: processed_into/converted_into. История происхождения результатов. |
| Idea | title, bodyMarkdown, reasonMarkdown?, lastReviewedAt?, status: incubating/archived/converted, convertedTargetType/id?. |
| Material | title, bodyMarkdown, status: active/archived. Без выполнения. |
| ContextLink | sourceType: material/idea, sourceId, targetType: project/task, targetId. Уникальная пара, связь с владельцем. |
| Session | ownerId, hashedOpaqueToken, expiresAt, lastUsedAt, deviceLabel, revokedAt. |
| ApiToken | ownerId, name, tokenPrefix, hashedSecret, scopes[], expiresAt, revokedAt, lastUsedAt. |
| AppliedOperation | ownerId, operationId, requestHash, outcome, appliedAt. Защита от повторов. |
| ChangeBatch | ownerId, sequence, operationId, changedEntities[], tombstones[]. Одна запись на транзакцию. |
| AuditEvent | actorKind/sessionId/tokenId, operationId, commandType, objectIds, outcome, timestamp. Без содержимого Markdown. |

Локальные служебные таблицы: outbox, confirmed snapshot, optimistic overlay, conflict versions, editor drafts, sync cursor. Они не смешиваются с серверными revision и статусами задач. Вложения и бинарные объекты не входят в модель R1.

Лимиты первой версии: title до 240 символов, логин до 128, Markdown-поле до 100 000 символов; пустой заголовок запрещён, Markdown может быть пустым. Команда до 2 МиБ UTF-8, пакет разбора до 50 результатов, страница чтения до 200 объектов. JSON-импорт до 50 МиБ; отчёт о превышении не меняет данные. Это технические пределы R1, не ограничения методики. При превышении клиент предлагает разбить ввод/импорт; сервер проверяет независимо.

Revision проекта также увеличивается при изменении состава и порядка его плана: создание/перенос/удаление/восстановление задач и ReorderProjectTasks. Это guard состава проекта для CloseProject и изменения порядка; отдельная неописанная версия коллекции не требуется. Одновременно созданная задача делает прежнюю revision проекта неактуальной. Для самостоятельных задач planPosition не используется.

Ссылки только на объекты того же владельца. Внешние Markdown-URL допускают http/https; другие схемы не активируются. В R1 вложенного дерева проектов и подзадач нет. Текстовые чек-листы остаются частью Markdown.

## 3. Инварианты и транзакции

1. В ActionQueue каждый taskId встречается максимум один раз; каждый ссылается на открытую неудалённую задачу активного проекта либо на самостоятельную задачу. Для таких задач `inActions=true`; для остальных false. Таблица очереди и флаг обновляются одной транзакцией.
2. SelectTask добавляет ID в конец; повторный выбор уже выбранного объекта — no-op. UnselectTask удаляет ID и сбрасывает флаг, не меняя status.
3. CompleteTask устанавливает done, completedAt и completedFromActions по прежнему флагу; удаляет из очереди и сбрасывает inActions. RestoreTask возвращает open, но не возвращает выбор автоматически. CancelTask также убирает из очереди. Это предлагаемое правило R1; текущий демонстрационный HTML не определяет серверную семантику восстановления.
4. Следующий шаг проекта вычисляется по первому подходящему taskId в общей очереди. Изменение его названия — UpdateTask; отдельного дублирующего поля в Project нет.
5. Перенос выбранной задачи в активный проект сохраняет выбор; перенос в paused/completed/cancelled запрещён, пока явно не снят выбор. Пауза/корзина проекта снимает выбор его задач; возобновление/восстановление не выбирает их снова.
6. CloseProject принимает решение для каждой открытой задачи: cancel, detach или moveToProjectId. Проверяет актуальность состава задач проекта и ревизии всех затронутых объектов. Новая параллельно созданная задача вызывает конфликт, а не остаётся незаметной в закрытом проекте.
7. ProcessInbox атомарно создаёт результаты/ContextLink/OriginLink, удаляет черновик и меняет статус исходника. Сбой любого результата откатывает всё. Обработанное входящее не разбирается повторно без отдельного явного редактирования результата.
8. ConvertIdea атомарно создаёт один результат и ссылку происхождения. Повтор operationId возвращает тот же результат. Повтор новой командой для уже converted-идеи даёт доменную ошибку со ссылкой на результат.
9. Материал существует независимо от контекстных связей. Удаление связи не удаляет запись. Удалённые объекты скрыты из обычных выборок, но сохраняют ID и связи в корзине.
10. Дата срока хранится `YYYY-MM-DD`; просрочка вычисляется относительно timeZone аккаунта со следующего дня. Изменение часового пояса не переписывает сохранённую дату. Оно не должно автоматически выбирать или завершать задачу.

## 4. Внешний контракт API

HTTPS, JSON, префикс `/api/v1`. Документ OpenAPI входит в репозиторий приложения и проверяется при сборке. Он должен описывать типы, nullability, лимиты, ошибки, scopes и примеры всех реализованных команд. Ни одна важная функция не должна быть доступна исключительно прямым запросом из web-клиента к БД.

### Чтение и команды

| Метод / путь | Назначение и доступ |
|---|---|
| GET /health/live, /health/ready | Состояние процесса/зависимостей без деталей и секретов; вне `/api/v1`. |
| GET /api/v1/me | Профиль владельца и зона. Сессия или разрешённый токен. |
| GET /api/v1/projects, /tasks, /inbox, /ideas, /materials | Типизированные списки; cursor/limit, status и projectId где применимо. Scope data:read. |
| GET /api/v1/{collection}/{id} | Объект, revision и связанные ID; чужой/отсутствующий объект → 404. |
| GET /api/v1/action-queue | Упорядоченные ID и revision; data:read. |
| GET /api/v1/search?q=… | Поиск по основным типам, лимит и cursor; data:read. Офлайн клиент выполняет аналогичный поиск локально. |
| POST /api/v1/commands | Одна доменная команда, идемпотентная по operationId; scope проверяется по типу команды. |
| GET /api/v1/sync/snapshot | Согласованный снимок пользователя и cursor; data:read. |
| GET /api/v1/sync/changes?cursor=… | Пакеты изменений, nextCursor, hasMore; data:read. |
| GET /api/v1/exports/json | Полный серверный экспорт; отдельный scope data:export или браузерная сессия. |
| GET /api/v1/exports/markdown | ZIP Markdown + manifest; те же права. |
| POST /api/v1/imports/validate | Проверить JSON, вернуть importId, hash, report; только сессия, повторный ввод пароля. |
| POST /api/v1/imports/{id}/commit | Подтвердить импорт в пустое пространство, operationId; только сессия. |

Чтение коллекций использует стабильный непрозрачный cursor, а не offset для синхронизации. deletedAt по умолчанию исключён; доступ к корзине — явный фильтр. Поиск R1: регистронезависимое совпадение по title и Markdown-тексту, без обещания семантического поиска и без передачи данных внешней модели.

### Envelope команды

```json
{
  "operationId": "018f21d8-8a82-4000-8000-000000000001",
  "deviceId": "browser-a",
  "type": "SelectTask",
  "expected": [
    {"entity":"task","id":"018f21d8-8a82-4000-8000-000000000002","revision":7},
    {"entity":"actionQueue","revision":12}
  ],
  "payload": {"taskId":"018f21d8-8a82-4000-8000-000000000002"}
}
```

Успешный ответ: operationId, outcome applied/noop, changedEntities с новыми revision и sequence для этой транзакции. Sequence ответа не заменяет cursor pull-синхронизации: клиент должен прочесть все предшествующие чужие изменения. Повтор того же operationId и payload возвращает сохранённый ответ; тот же operationId с другим requestHash → 409 idempotency_mismatch.

Для Create-команд клиент передаёт UUID; expected revision не требуется для нового ID. Для Update/Delete требуется expected revision, для изменения членства/порядка — также revision очереди, для составных операций — ревизии всех затронутых объектов и guard версии состава проекта. Сервер определяет полный read/write set; неполный expected не отключает проверку, а даёт 422 missing_precondition.

| Команды | Основной payload |
|---|---|
| CreateTask / UpdateTask | id для create; taskId для update; title, projectId?, notesMarkdown?, dueDate?; update только изменяемые поля, omitted означает не менять |
| SelectTask / UnselectTask / CompleteTask / RestoreTask / CancelTask | taskId; указанные выше ревизии |
| ReorderActions | полный orderedTaskIds текущей очереди; сервер проверяет точное множество |
| ReorderProjectTasks | projectId, orderedTaskIds плана; independent revision состава |
| CreateProject / UpdateProject | title, visionMarkdown?, targetMarkdown?, planMarkdown? |
| PauseProject / ResumeProject / CloseProject | projectId; для close итоговый статус и decisions по открытым taskId |
| CaptureInbox / UpdateInbox | bodyMarkdown, sourceLabel? |
| SaveProcessingDraft / ProcessInbox | inboxId, outputs[] с типом/id/полями, links[]; ProcessInbox полностью проверяет ссылки внутри пакета |
| CreateIdea / UpdateIdea / ReviewIdea / ArchiveIdea / ConvertIdea | поля идеи; при convert targetType: task/project и target с ID |
| CreateMaterial / UpdateMaterial / ArchiveMaterial | title, bodyMarkdown |
| AddContextLink / RemoveContextLink | sourceType/id, targetType/id |
| TrashEntity / RestoreEntity | entityType, entityId; поддерживаемые типы строго перечислены |
| UpdateSettings | timeZone; без auth-настроек |

При разработке расширить эту таблицу до исчерпывающих схем OpenAPI/валидаторов, включая все статусы и ограничения. В частности, никакого произвольного `patch` к внутренним полям ownerId/revision/passwordHash. Auth-объекты не проходят через универсальные команды данных.

Ошибка возвращает `{error:{code,message,fieldErrors?,conflict?,retryAfter?},requestId}`. 400 — формат, 401 — нужен вход, 403 — недостаточный scope, 404 — объект недоступен, 409 — конфликт/повтор с другим содержимым, 413 — размер, 422 — нарушенное доменное правило, 429 — ограничение, 5xx — временный сбой. Для 409 возвращать текущие доступные клиенту версии и идентификаторы затронутых объектов, не чужие данные.

## 5. Вход, сессии и токены

R1 web: POST `/auth/login` с login/password создаёт opaque server session в Secure HttpOnly SameSite cookie; `/auth/logout` отзывает её, `/auth/sessions` показывает устройства, DELETE `/auth/sessions/{id}` отзывает выбранную, POST `/auth/password` меняет пароль после проверки текущего. Все пути под `/api/v1`. Предлагаемые сроки: idle 7 дней, absolute 30 дней; серверные настройки с документированными значениями.

Cookie-команды защищать CSRF-токеном и проверкой Origin. CORS закрыт для чужих браузерных origins; серверные интеграции используют Bearer API-токен. Пароль хранить через поддерживаемую библиотеку Argon2id с уникальной солью, параметры проверить по [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) и замеру на сервере. Пароли и токены не хранить открыто. Предлагаемая политика: 15–128 символов, разрешён пароль-фраза и вставка из менеджера, без принудительных смен по календарю; rate limit по аккаунту и IP, единое сообщение неверного входа.

API-токены управляются `/api/v1/auth/api-tokens`: создать/получить метаданные/отозвать. Создание требует свежего подтверждения паролем, секрет показывается один раз, сервер хранит хеш. Обязательны имя, срок окончания (предложение по умолчанию 90 дней) и явный набор scopes:

- `data:read` — чтение обычных данных и sync;
- `inbox:create` — только CaptureInbox, без чтения очереди;
- `data:write` — команды основных сущностей, кроме настроек, auth и массового импорта;
- `data:export` — выгрузки, не наследуется из data:read.

Каждый endpoint проверяет право независимо. Токен с data:write не управляет паролями, сессиями и другими токенами. В ответах запрещённого чтения не возвращать содержимое объекта. Журнал аудита отличает пользователя от конкретной интеграции.

Будущие Android/iOS-клиенты потребуют отдельного потокa входа и ротации refresh-токенов, с хранением в защищённом хранилище ОС. Это адаптер аутентификации R2; данные и команды `/api/v1` сохраняются. Не выдавать нативным клиентам долгоживущий пароль или PAT в роли обычной пользовательской сессии. Публикация auth endpoints R2 до реализации и проверки не требуется.

Смена/сброс пароля отзывает остальные сессии; отзыв API-токенов предлагается отдельным явным выбором. Удалённый отзыв запрещает серверный доступ, но не способен гарантированно стереть офлайн-кэш на отключённом устройстве. Без E2EE данные на сервере читаемы приложением; защита локального устройства остаётся важной, не обещать шифрование, которого нет.

## 6. Локальная БД и синхронизация

### Запись и отправка

1. Клиент создаёт operationId и проверяет команду локально. В одной IndexedDB-транзакции сохраняет изменение в optimistic overlay и outbox-команду. Только затем показывает локальный успех.
2. На аккаунт работает один sync worker; вкладки координируются через доступный механизм блокировки с fallback-выбором лидера. UI подписан на изменения локальной БД. Прототипный localStorage не используется как БД продукта.
3. Очередь сохраняет зависимости: создание проекта до задачи, изменение задачи до её выполнения. Клиент назначает server expected revision при отправке: первый edit опирается на confirmed revision, следующий зависимый edit — на ack предыдущего. OperationId и payload уже отправленного запроса неизменны; после конфликта новая попытка — новый operationId.
4. Worker последовательно отправляет команды. Повторы только для сетевых ошибок/5xx/429 с тем же operationId, exponential backoff с jitter до 60 с. При 401 приостанавливает отправку до входа, при 409 — затронутую цепочку, при 422 — сохраняет ошибку для исправления. Независимые объекты могут синхронизироваться дальше.
5. Server commit атомарно меняет данные, пишет AppliedOperation, ChangeBatch и audit. При ответе клиент переносит результат в confirmed snapshot и убирает подтверждённую outbox-команду одной локальной транзакцией.

### Получение изменений и порядок

Каждый ChangeBatch содержит целую транзакцию; пакет не разбивается между страницами. Сервер сериализует выделение sequence в пределах владельца под блокировкой транзакции, чтобы поздний commit не получил sequence меньше уже выданного cursor. Poll активного клиента — каждые 5 с, немедленно при foreground, online и ack; WebSocket для R1 не обязателен.

Получение страницы и смена cursor атомарны локально. Server snapshot возвращается из согласованного снимка БД вместе с соответствующим cursor. Если snapshot требует пагинации, все страницы принадлежат одному snapshotId с фиксированной границей; нельзя смешивать независимые страницы живой БД.

Чужие изменения без local pending применяются сразу. При pending по объекту новые серверные данные сохраняются рядом с локальной версией; overlay не затирается. Если менялись разные поля, R1 вправе всё равно показать конфликт целого объекта; автоматическое текстовое слияние не является обязательным. Пользовательское объединение создаёт новую команду на актуальной revision и может снова конфликтовать при новом редактировании.

Для ActionQueue конфликт сравнивает состав и порядок целиком. UI даёт выбрать/собрать итоговый порядок, исключая уже выполненные/удалённые задачи. Составной разбор конфликтует как единый пакет, а не частично превращается в новые независимые create-запросы. Для сохранения «обеих версий» нового объекта сервер создаёт новые UUID и связи по явному подтверждению.

### Долгое отсутствие, удаление и потеря ответа

AppliedOperation хранится на время жизни аккаунта (минимум operationId/requestHash/outcome и IDs результатов). Повтор после потери ответа безопасен. Change log можно хранить 90 дней; старый cursor получает 410 resync_required. Клиент сохраняет outbox/overlay/конфликты, получает полный снимок и повторно проверяет pending against current revisions, не стирая локальную работу.

Корзина хранит содержимое 30 дней; после очистки остаётся tombstone ID/revision. UUID не переиспользуются. Старое офлайн-редактирование очищенной записи возвращает конфликт удалённого объекта, с возможностью сохранить локальное содержание новой записью. Массовый импорт выполняется как один атомарный набор изменений либо как опубликованный снимок с принудительной resync, не как частично видимые записи.

### Границы PWA

Service worker кэширует оболочку и ресурсы своей версии. API-ответы с личными данными не складываются в общий HTTP-cache; ими управляет локальная БД аккаунта. Смена пользователя использует отдельную БД. При выходе с pending предложить синхронизацию или локальный экспорт до удаления кэша; удаление без сохранения требует явного выбора.

Запросить persistent storage там, где доступно, обрабатывать отказ и QuotaExceededError. Браузерное хранилище не гарантирует вечную сохранность и может быть очищено пользователем или браузером; это ограничение отражено в [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria). До первой синхронизации единственная копия изменения может находиться на устройстве: UI показывает это, не обещает серверный backup.

## 7. Экспорт и восстановление

JSON содержит formatVersion, exportedAt, accountTimeZone, сущности, очередь, связи, корзину и origin links. Credentials, cookie, API-токены и серверные внутренние логи исключены. Локальная выгрузка содержит актуальный пользовательский overlay, список pending/conflict и обе конфликтующие версии в recovery-разделе; transport metadata не становится исполняемой командой при импорте.

Validate проверяет размер, схему, UUID, ссылки, повторяющиеся ID, статусы, длины, очередь и совместимость версии. Для конфликтного recovery-экспорта перед commit предложить выбрать версии; при необходимости сохранить вторую копией. ImportId связан с владельцем и hash неизменяемого файла, действует 24 часа. Commit проверяет, что пространство пусто, и импортирует атомарно с новыми серверными revision, сохраняя пользовательские ID; ownerId заменяется текущим. Повтор import operationId идемпотентен. Импорт в заполненное пространство R1 отклоняет с объяснением.

Markdown ZIP формируется из того же пользовательского снимка. Имена очищены от путей/служебных символов, для связей используется manifest и относительные ссылки. Archive extraction при JSON-восстановлении не требуется. Markdown-выгрузка не содержит секретов и не обещает поддержку всех расширений Obsidian.

Резервные копии PostgreSQL: ежедневное выполнение, проверка кода выхода и контроль свежести, ротация 30 дней, хранение отдельной копии вне сервера. Перед разрушительной миграцией — свежая копия и проверенный способ отката/восстановления. Backup-ключи не лежат в репозитории и доступ ограничен оператором. В инструкции описать отдельно восстановление БД сервера и пользовательского JSON: это разные сценарии.

## 8. Расширение инструментами и дальнейшие этапы

В R1 API и доменные команды — единая точка расширения. Не создавать общий plugin runtime заранее. Для встроенного инструмента позже потребуется: конкретная функция, провайдер, набор scopes, источник credentials, данные на выход за пределы сервера, preview результата, подтверждение побочных эффектов, отмена/timeout и аудит. Чтение содержимого заметок не даёт инструменту разрешения выполнять инструкции из этих заметок.

Импорт Obsidian — будущий отдельный read-only адаптер чтения выгрузки/копии, с dry-run и отчётом сопоставления; исходное хранилище не изменяется. E2EE — отдельное проектирование ключей, восстановления доступа, локального поиска и работы инструментов. Нельзя заявить, что E2EE добавится переключателем: серверный поиск и интеграции потребуют пересмотра. Десктопное приложение сейчас не проектируется.
