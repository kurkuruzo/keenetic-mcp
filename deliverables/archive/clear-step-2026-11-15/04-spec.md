# Техническое задание

Версия 1.0 от 14.11.2026. Назначение: реализация личной PWA «Ясный шаг» для одного владельца на компьютере и телефоне. Требования ниже относятся к продукту, а не к демонстрационному HTML.

## 1. Границы и приоритеты

Обязательные P0: надёжный захват, разбор с несколькими результатами, плоские действия, проекты, обзоры, события, идеи, материалы, ожидания, доступ на двух устройствах, офлайн после первого входа, экспорт/восстановление. P1: фокус-сессии и настройка источников входящих; реализовать до релиза описанного MVP. Всё из колонки последующих версий в описании продукта — вне этой поставки.

Сначала реализовать вертикальный сценарий захвата и разбора на локальном хранилище; готовность этого этапа не означает готовность MVP. Релиз возможен только после проверки синхронизации и восстановления. Прототипные данные не мигрируются в продукт.

## 2. Предлагаемая архитектура

Предложение, которое агент может уточнить через ADR до начала реализации: TypeScript, React для адаптивного клиента, IndexedDB для локальной базы, service worker для оболочки PWA, Node.js HTTP API и PostgreSQL на сервере. Версии и конкретные библиотеки выбрать по поддерживаемым стабильным релизам на старте реализации, закрепить lock-файлом. Этот документ не утверждает конкретные версии актуальными.

Слои: UI → команды домена → транзакционный локальный repository → outbox синхронизации → серверный API → серверная БД. Валидация и команды домена общие для клиента и сервера там, где это возможно. Доступ к IndexedDB и HTTP не размещать внутри компонентов. Сервер — источник межустройственных ревизий; локальная база — источник UI во время работы.

Для входа использовать проверенного OIDC-провайдера с серверной сессией в Secure/HttpOnly/SameSite cookie. Самостоятельную систему паролей не разрабатывать. Клиент и API предпочтительно одного origin. Разрешён один владелец аккаунта; новая регистрация закрыта по умолчанию. Конкретный провайдер и размещение — конфигурация окружения, публичное развёртывание не входит в задание.

## 3. Модель данных

Все пользовательские объекты: `id` (UUID, генерируется клиентом), `ownerId`, `createdAt`, `updatedAt` (UTC), `revision` (целое серверное), `deletedAt` nullable. Клиентские часы не решают конфликты. Локальные служебные поля `syncStatus` и `lastSyncedRevision` не включать в доменную идентичность. Текст хранить как plain text; HTML из пользовательского ввода не исполнять.

| Сущность | Поля сверх общих | Назначение |
|---|---|---|
| InboxItem | text, sourceUrl?, sourceName?, state: unprocessed/processed, processedAt? | Необдуманное входящее; удаление через deletedAt |
| ProcessingDraft | inboxId, draftVersion, outputs[], updatedByDevice | Сохраняемый набор ещё не принятых результатов |
| ProcessingLink | inboxId, targetType, targetId, batchId | История одного входящего и всех его результатов |
| Task | title, notes, projectId?, state: active/waiting/done/cancelled, horizon: now/week/later, selectedForDate?, selectedWeek?, rank, dueDate?, completedAt?, cancelledAt? | Только исполнимое ближайшее действие |
| Project | title, desiredOutcome, purpose?, minimumOutcome?, planText?, state: active/paused/done/cancelled, completedAt? | Конечный результат; план не является очередью действий |
| Event | title, startsAt?, endsAt?, timeZone, allDay, startDate?, endDateExclusive?, location?, projectId?, notes | Выделенный интервал либо событие на весь день |
| Material | title, body, url?, projectId?, taskId?, useContext? | Справочная информация, без статуса выполнения |
| Idea | title, body, reason?, lastReviewedAt?, state: incubating/converted/archived, convertedProjectId? | Необязательный замысел |
| Waiting | personText, expectedResult, checkOn, projectId?, taskId?, state: open/received/cancelled, controlTaskId? | Личный контроль договорённости |
| ReviewSchedule | kind: daily/weekly, timeZone, localTime?, weekday?, enabled | Периодичность появления обзора внутри приложения |
| ReviewSession | kind, periodKey, state: in_progress/completed/partial, stepsSnapshot[], startedAt, finishedAt? | Фактическое прохождение, отдельно от расписания |
| ReviewStep | key, state: pending/done/skipped, note?, deferredTaskId? | Часть snapshot с явным решением |
| InboxSource | name, instruction?, enabled, lastCheckedAt? | Ручной список источников; интеграций нет |
| FocusSession | taskId, state: running/paused/finished/abandoned, durationSeconds, remainingAtPause?, endsAt?, startedAt, finishedAt? | Независима от выполнения задачи |
| TaskHistory | taskId, previousTitle, newTitle, changedAt | След переформулировки |
| Settings | timeZone, weekStartsOn=Monday, review settings | Персональные настройки |

UUID и ссылки валидируются сервером в пределах владельца. `title`: 1–240 символов после trim; входящее и body/notes/planText — до 20 000 символов; URL — до 2048 символов, только http/https. Пустые обязательные значения отклоняются. Лимиты — продуктовые, одинаковые на клиенте и сервере.

В MVP у действия максимум один проект. Материал может быть связан и с задачей, и с её проектом; противоречивую связь отклонить. Проект — общий UI-термин для конечного дела, даже если путь неизвестен. Постоянные области жизни пока отражаются в тексте/контексте, не требуют отдельной сущности цели или дерева папок.

## 4. Правила команд

### F01. Захват

`CaptureInbox(text, sourceUrl?)`: в одной локальной транзакции создать запись и outbox-операцию. Подтверждать сохранение только после commit IndexedDB. Повторный submit с тем же operationId не дублирует запись. Пустой текст не принимать. Быстрый ввод не требует категорий и дат. При ошибке сохранять содержимое поля.

### F02. Разбор

`ProcessInbox(inboxId, baseRevision, outputs[], operationId)`: разрешён только для необработанного неудалённого входящего. Один output может иметь тип Task, Project, Event, Material, Idea; количество 1–50. ID новых объектов генерируются заранее, поэтому задача может ссылаться на проект в этом же пакете. Валидация всех объектов и ссылок выполняется до изменения состояния.

В одной транзакции создать результаты и ProcessingLink, отметить исходник processed и удалить соответствующий черновик. При ошибке ни один результат не считается принятым, исходник остаётся unprocessed. Повтор доставки operationId возвращает прежний ответ. Второй разбор того же входящего с другим operationId и старой ревизией — конфликт; не создавать копии молча.

«Не нужно» — отдельная команда перемещения входящего в корзину без outputs. Текст исходника не уничтожать. Undo разбора допустим, если созданные результаты не были изменены и не имеют новых зависимостей: вернуть входящее и убрать результаты транзакционно. В противном случае показать ссылки и предложить ручное исправление; не удалять последующую работу.

### F03. Действия и время

Active → done или cancelled или waiting; done/cancelled → active по явному восстановлению. Waiting → active после снятия ожидания. Активное действие с проектом paused/done/cancelled не показывать среди исполнимых. При работе с фильтрами учитывать и состояние проекта.

`now` требует `selectedForDate` (локальная дата пользователя). После смены дня запись не меняется автоматически: попадает в «Предыдущий выбор» обзора. В «Сейчас» выводятся только active с today. `week` требует ISO-даты начала выбранной недели; старые недельные выборы видны в обзоре. `later` не требует даты. Изменение горизонта очищает неактуальные поля выбора.

`dueDate` — отдельная локальная календарная дата реального срока. Просрочка наступает со следующего дня в зоне аккаунта; её наличие не переносит действие в «Сейчас» автоматически. Приоритет — ручной rank в рамках горизонта/даты. Упорядочивание при одинаковом rank стабилизировать id; обновлять порядок транзакционно через команду со списком id, не полагаться на бесконечные дробные значения.

При редактировании title записывать TaskHistory. Подсказка о нечёткой формулировке не блокирует сохранение; никакой грамматический алгоритм не объявлять объективной оценкой. Поиск: подстрока без учёта регистра по title/notes, с фильтрами состояния и проекта; по умолчанию исключить корзину.

### F04. Проекты

Желаемый результат обязателен. Если нет доступного ближайшего действия и нет открытого ожидания, активный проект получает вычисляемую пометку «Нужен следующий шаг». Завершение действия не завершает проект. При закрытии проекта явно выбрать для незавершённых задач: отменить, отвязать или перенести в другой активный проект. Запретить завершение без решения по каждой такой задаче. Команда атомарная.

Пауза сохраняет задачи, но исключает их из рабочих очередей. Возобновление переводит незавершённые действия в later и предлагает пересмотр. Удаление проекта — в корзину с возможностью восстановления; связанные материалы и задачи не удалять каскадом. Пока проект удалён, связанные действия видны в отдельном разделе обзора «Нужен контекст», не теряются.

### F05. Ожидания

Создание Waiting с taskId переводит задачу в waiting транзакционно. Ожидание без задачи тоже допустимо. Достигнутая `checkOn` лишь показывает запись в обзоре. «Создать действие контроля» создаёт отдельный active Task и controlTaskId; пока эта задача открыта, повторная команда возвращает её вместо копии. После её завершения можно создать следующее действие контроля.

«Результат получен» закрывает ожидание, а связанную исходную задачу возвращает в active/later для осмысления результата. Завершение задачи пользователь подтверждает отдельно. Никакие сообщения другому человеку автоматически не отправлять.

### F06. Обзоры

Уникальный ключ сессии: ownerId + kind + periodKey (дата или понедельник недели в зоне аккаунта). Повторное открытие продолжает существующую сессию. Состав шагов копируется в snapshot; изменение шаблона не ломает текущий обзор. Пропущенные дни не порождают очередь новых сессий. Есть текущий период и отдельный незаконченный обзор, который можно продолжить или закрыть как partial.

Состояния шагов: pending → done/skipped; можно вернуть в pending. Завершение разрешено при отсутствии pending; при любом skipped итог partial, иначе completed. «Сохранить и выйти» не завершает обзор. Для отложенной части можно создать отдельную задачу, шаг отмечается skipped с deferredTaskId. Считать дату последнего полного и частичного обзора отдельно.

В ежедневном обзоре показывать предыдущий now, завершённое за день, проекты после выполненных шагов, события ближайшего дня и реальные сроки. В еженедельном — источники входящих, все активные действия, проекты без шага, открытые ожидания, завершённое за 7 дней, события на 14 дней, план недели. Выбор новых задач всегда ручной; приложение не считает, что свободные часы гарантируют их выполнение.

### F07. Идеи, материалы, события

Сортировка идей: lastReviewedAt ascending, отсутствующее значение считать createdAt, затем id. Просмотр карточки не меняет lastReviewedAt; это делает кнопка «Пересмотрено». Превращение в проект атомарно создаёт проект и устанавливает convertedProjectId/state. Повтор операции не создаёт дубликат. Архивирование идеи не означает её выполнение.

Материалы — CRUD, поиск, ссылки и контекст. Внешние URL открывать безопасно, без загрузки их содержимого на сервере. События: для timed обязателен endsAt > startsAt и IANA timeZone; для allDay использовать только даты с исключающей правой границей. Не смешивать эти представления. Отображать в зоне аккаунта, исходную зону показывать в карточке. Встреча не превращается в задачу автоматически.

### F08. Фокус

Одна незаконченная сессия на устройстве. Таймер считает остаток относительно endsAt, а не количеством срабатываний setInterval. При паузе сохраняет остаток. После сна/перезагрузки пересчитывает состояние, не создаёт отрицательное время. При окончании сессия finished, но задача остаётся active до отдельного подтверждения. Нажатие «Выполнено» завершает задачу и сессию. Захват отвлечения не останавливает сессию и не переводит пользователя в разбор.

## 5. API и синхронизация

API одной версии, JSON, явные коды ошибок; каждый изменяющий запрос содержит `operationId` и `baseRevision` изменяемых объектов. Команды проверяются доменным слоем сервера. Сессия пользователя определяет ownerId; присланный клиентом ownerId не даёт прав доступа.

| Endpoint | Назначение |
|---|---|
| GET /api/v1/bootstrap | Снимок данных аккаунта + cursor для первой синхронизации |
| POST /api/v1/commands | Одна доменная команда; атомарные составные операции |
| GET /api/v1/changes?cursor=… | Упорядоченные изменения и tombstones с nextCursor |
| GET /api/v1/export | Версионированный JSON всего пользовательского содержимого |
| POST /api/v1/import/validate | Проверка файла и отчёт о предполагаемых изменениях |
| POST /api/v1/import/commit | Атомарное применение подтверждённого валидного набора |
| GET /api/v1/session | Состояние входа, без раскрытия токенов |

Команды: CaptureInbox, SaveProcessingDraft, ProcessInbox, DiscardInbox, UpdateTask, CompleteTask, CancelTask, RestoreTask, ReorderTasks, CreateProject, UpdateProject, PauseProject, ResumeProject, CloseProject, CreateWaiting, ResolveWaiting, CreateControlTask, UpsertEvent, UpsertMaterial, UpsertIdea, ReviewIdea, ConvertIdea, StartReview, UpdateReviewStep, FinishReview, UpsertFocus, UpdateSettings, Trash, Restore. Точные payload-схемы зафиксировать в общем типизированном пакете; публичный OpenAPI генерировать из схем, не поддерживать вручную вторую противоречивую схему.

Пример составной команды:

```json
{
  "operationId": "UUID операции",
  "type": "ProcessInbox",
  "payload": {
    "inboxId": "UUID входящего",
    "baseRevision": 4,
    "outputs": [
      {"type": "Project", "id": "UUID проекта", "title": "Семейная поездка", "desiredOutcome": "Согласованы даты и забронировано жильё"},
      {"type": "Task", "id": "UUID задачи", "title": "Написать семье и предложить две даты", "projectId": "UUID проекта", "horizon": "later"}
    ]
  }
}
```

Строки UUID в примере обозначают места для настоящих UUID, не буквальные валидные значения.

### Протокол

1. Локальная транзакция одновременно применяет команду и записывает outbox. UI видит pending.
2. Один worker отправляет команды последовательно, с повтором после сетевых ошибок и backoff до 60 секунд. При возвращении сети или foreground — немедленная попытка. Уникальность operationId сервер обеспечивает постоянной таблицей обработанных команд на время жизни аккаунта.
3. Сервер применяет транзакцию и записывает последовательный change log. Клиент удаляет outbox только после подтверждения; разрыв после server commit безопасен благодаря operationId.
4. Клиент читает изменения по cursor. Применение страницы и обновление cursor атомарны. При истёкшем cursor сервер отвечает `resync_required`; клиент получает снимок, не теряя локальные pending-команды.
5. Пока есть pending на объект, серверную версию хранить отдельно, не затирать локальное редактирование. При совпавшей baseRevision сервер принимает команду. При расхождении — 409 с обеими версиями; последующие команды по затронутым объектам приостанавливаются.
6. В конфликте пользователь выбирает серверную, локальную или сохраняет локальное содержание копией. Повторное применение основано на новой серверной ревизии. Для составного разбора конфликт решается целым пакетом; нельзя частично повторить его как набор независимых вставок.

Удаление тоже является ревизионным изменением. В конфликте edit/delete показать удалённую и локальную версии. Не «воскрешать» молча удалённые данные. Корзина хранится 30 дней, после чего контент удаляется, но tombstone с id/revision остаётся для синхронизации. Устройство после длительного отсутствия получает актуальный снимок и явно разрешает свои старые pending-команды.

Ошибки: 400 неправильная схема, 401 нужен вход, 403 чужой объект, 409 конфликт, 413 размер, 422 доменное нарушение, 429 ограничение, 5xx временный сбой. Пользователю показывать действие для исправления; текст задачи и секреты в логи не писать.

## 6. Даты, безопасность, восстановление

Часовой пояс задаётся IANA-идентификатором в Settings, первоначально предлагается зона устройства. Его смена не переписывает абсолютные времена событий; локальные даты намерений и сроков остаются прежними. Неделя начинается в понедельник. DST: события хранят абсолютные UTC-интервалы и исходную зону; неоднозначное локальное время требует выбора смещения, несуществующее отклоняется с объяснением. Переход суток проверяется при foreground и по локальному таймеру, без массового редактирования задач.

Все серверные выборки изолированы по владельцу; тест доступа чужого UUID обязателен даже при одном пользователе в первой установке. Защита CSRF для изменяющих cookie-запросов, строгая проверка Origin, TLS при размещении, CSP, ограничение запросов входа, безопасная обработка текста и ссылок. Секреты только в окружении сервера. Аналитика не получает содержимое записей. На сервере и клиенте не обещать E2EE: она вне MVP.

На выходе, если есть несинхронизированные данные, предложить синхронизировать или экспортировать локальную копию. Не очищать локальную базу молча. При смене аккаунта базы разделяются по ownerId; никакие данные прежнего пользователя не становятся видимыми новому.

Экспорт содержит schemaVersion, exportedAt, timeZone, все сущности и связи, включая историю, архив и корзину, но не сессионные токены и outbox transport metadata. Локальный экспорт включает pending-содержимое и ясно сообщает, что сервер мог ещё его не получить. Импорт сначала полностью валидируется (размер до 20 МБ для MVP, ссылки, перечисления, даты, UUID), показывает количество объектов и конфликты. По умолчанию импортирует как копию с переназначением всех UUID и связей; перезапись аккаунта не входит в MVP. Commit атомарный; operationId предотвращает повторное применение одной подтверждённой попытки.

Для серверной установки: ежедневная резервная копия БД, хранение 30 дней, описанная команда восстановления в отдельную БД. Цель RPO ≤24 ч для серверной аварии, RTO ≤4 ч при доступном хосте и копии; это эксплуатационные цели, подтверждаемые восстановлением, а не автоматическая гарантия. Периодически напоминать о возможности пользовательского экспорта в настройках, без навязчивого push.

## 7. Нефункциональные требования

- Интерфейс на русском; строки вынесены в ресурсы. Desktop и mobile, ширина от 360 px, клавиатура и скринридер, требования доступности из спецификации экранов.
- После первой успешной онлайн-загрузки можно открыть оболочку, читать локальные данные, записывать и редактировать без сети. Первый вход и восстановление на новом устройстве требуют сети.
- На зафиксированном тестовом устройстве при 10 000 задач: локальный список и поиск p95 ≤300 мс; подтверждение обычного локального сохранения p95 ≤200 мс; при большей задержке — индикатор. Условия измерения зафиксировать в отчёте, не выдавать настольный тест за телефонный.
- При обоих активных устройствах и рабочей сети изменения появляются на втором ≤10 секунд в 95% проверок. Фоновая вкладка/закрытое приложение не обязаны синхронизироваться до открытия.
- Обновление service worker не должно перезагружать страницу с несохранённым вводом. Миграции локальной БД транзакционные, с обработкой ошибки и сохранением старых данных.
- Журналы содержат operationId, тип команды, код результата и длительность; содержимое задач и URL пользователя исключается.

## 9. Критерий готовности

Все P0/P1 этой версии реализованы; A01–A23 пройдены либо формально исключены владельцем с изменением объёма версии. Есть миграции, инструкции запуска и размещения, пример окружения без секретов, экспорт/импорт, проверенное восстановление и отчёт о фактических проверках. Ни прототип, ни локальный happy path, ни один зелёный unit-тест не являются доказательством готовой межустройственной системы.
