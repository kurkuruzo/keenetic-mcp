# Работа с роутерами пользователя

При добавлении роутера, восстановлении доступа или настройке его MCP-профиля
следуй порядку ниже. Это локальные соглашения для данного checkout на Windows;
общее устройство сервера описано в [README.md](README.md), хранение паролей —
в [SECURITY.md](SECURITY.md).

## Отдельный профиль на каждый роутер

- Профили находятся в `%APPDATA%\keenetic-mcp\<profile>`. Для мастера и запуска
  одного профиля каталог задаёт `KEENETIC_CONFIG_DIR`. Для нескольких профилей
  в Codex каталог каждого задаёт аргумент `--profile имя=абсолютный-путь`.
- Существующие имена: `osharskaya`, `fuchika`, `fedoseenko`, `almaty`,
  `akzholtai`, `lianozovo`, `brinskogo`. Перед работой проверь текущие каталоги
  и секции `%USERPROFILE%\.codex\config.toml`: это источник актуальных путей.
- `config.json` содержит только `host` и `login`. На Windows пароль хранится
  в `secrets.dpapi.json`, зашифрованном DPAPI CurrentUser. Профиль работает
  в контексте того Windows-пользователя, который сохранял пароль.
- Пароль привязан к точному сочетанию `login@host`. При смене адреса запускай
  мастер для нового адреса; простая замена host не переносит учётные данные.
- Используй отдельные профили, сохраняя существующие. Пароли вводятся локально
  скрытым вводом; не помещай их в чат, аргументы процессов, TOML, Git или логи.
  Использование учётных данных другого роутера допустимо только после явного
  указания пользователя, какого именно. Не перебирай сохранённые пароли.

## Подключение нового роутера

1. Уточни адрес управления и проверь `GET http://<host>/auth` с этого компьютера.
   Ответ 401 с заголовком `X-NDM-Realm` означает доступность Keenetic API,
   но ещё не успешную авторизацию. Тайм-аут сначала требует проверки сети.
2. Найди `node.exe` через `Get-Command node.exe`, проверь наличие `dist/index.js`.
   Используй работающий локальный сервер по абсолютному пути. Если сборки нет,
   выполни установку зависимостей и сборку согласно README/package.json.
3. Если отдельного рабочего профиля ещё нет, открой пользователю интерактивный
   терминал и запусти мастер с каталогом нового профиля, например:

   ```powershell
   $env:KEENETIC_CONFIG_DIR = Join-Path $env:APPDATA 'keenetic-mcp\brinskogo'
   $nodePath = (Get-Command node.exe).Source
   & $nodePath 'C:\Users\MK\development\keenetic-mcp\dist\index.js' init
   ```

   В мастере пользователь вводит адрес, логин и скрытый пароль. Укажи нужный
   адрес явно: предложенный мастером шлюз может относиться к домашнему роутеру.
   Мастер проверяет авторизацию, сохраняет пароль через защищённое хранилище
   и затем записывает config.json. Дождись успешного завершения пользователем.
   Ошибка мастера не означает созданный профиль. Проверь сохранённый host/login,
   не выводя содержимое хранилища паролей.
4. Добавь профиль в аргументы общей секции `[mcp_servers.keenetic-routers]`
   в `%USERPROFILE%\.codex\config.toml`, сохраняя остальные настройки.
   Образец структуры (пути сначала проверь на хосте):

   ```toml
   [mcp_servers.keenetic-routers]
   command = 'C:\absolute\path\to\node.exe'
   args = [
     'C:\absolute\path\to\keenetic-mcp\dist\index.js',
     '--profile', 'osharskaya=C:\Users\MK\AppData\Roaming\keenetic-mcp\osharskaya',
     '--profile', 'brinskogo=C:\Users\MK\AppData\Roaming\keenetic-mcp\brinskogo',
   ]
   ```

   Используй префикс профиля в имени инструмента, например
   `brinskogo_get_system_info`. Старые отдельные секции `keenetic` и
   `keenetic-<profile>` могут оставаться отключёнными для отката.
5. Проверь авторизованное чтение модели/прошивки через новый MCP. Если текущий
   чат ещё не видит новые инструменты, проверь RCI локальным клиентом проекта:
   `createSecretStore` + `spawnRunner` из `dist/config/secrets.js`,
   `read(login + '@' + host)` и `createClient` из `dist/router/client.js`.
   Пароль передавай только в памяти. Успешный RCI подтверждает учётные данные,
   но не загрузку секции текущим чатом; сообщи о возможной необходимости
   перезапуска Codex для появления инструментов.

## Если управление через VPN недоступно

- Проверяй маршрут, AllowedIPs на обоих концах, ACL и обратный путь отдельно.
  Online peer/handshake и успешный ping не доказывают доступность TCP/80.
- Учитывай реальный источник: домашний роутер и компьютер за ним имеют разные
  адреса. Транзит через Ошарскую сам по себе не заменяет источник её адресом;
  NAT проверяй на соответствующих роутерах. Не предполагай его наличие.
- Для HTTP API нужен TCP/80 к адресу управления. Разрешение ICMP его не открывает.
  При правке сети сначала прочитай актуальные настройки и сделай резервную копию;
  подключение MCP само по себе не требует менять или сохранять конфиг роутера.

## Сетевые заметки

После прямой проверки обновляй соответствующую заметку и общую схему в
`C:\Users\MK\obsidian\02 Контекст\Геликон\Области\Инфраструктура\Сеть филиалов`.
Отделяй локальные сети, AllowedIPs и маршруты. Сохраняй исторические сведения;
не найденное помечай рядом комментарием с фактической датой проверки.
Публикуй только выбранные поля: сырой RCI/config может содержать ключи и пароли.
